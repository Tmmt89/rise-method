# Контракт курса и учебного пакета

Версия 0.1.0. Это **формат проектирования методики**, а не JSON для прямого импорта в RiseAcademy. Поддерживаемые способы авторинга определяются [картой платформы](platform-fit.ru.md). Обозначения — в [словаре](../GLOSSARY.md).

## 1. Brief: что необходимо установить

| Поле | Содержание и проверка |
|---|---|
| `brief_id`, `version`, `owner_context` | Устойчивый ID, версия, курс/школа, источник запроса. |
| `course_intent` | Какую жизненную, рабочую, академическую или экзаменационную задачу решает обучение. Тема «Travel» сама по себе недостаточна. |
| `learners` | Возрастная группа, известный уровень и источник этой оценки, опыт именно нужного действия, число участников, literacy, существенные потребности. Неизвестное хранится отдельно. |
| `delivery` | Live/self-study/blended, длительность и частота, individual/pair/group, доступные роли, устройства, формат выхода и ресурсы. |
| `needs_evidence` | Интервью/образец/диагностическая попытка/наблюдение; что именно они подтверждают. |
| `constraints` | Программа, школьные нормы с областью действия, контент/визуальные условия, доступ к медиа, сроки. |
| `assumptions` | Допущение, основание, зависимое решение, способ проверки. Существенное неизвестное не заменяется выдуманной диагностикой. |
| `request_scope` | Курс/модуль/занятие/активность/адаптация; требуемые выходные артефакты. |

Если уровень задан только ярлыком B1, можно составить черновик с этим допущением. Нельзя написать «ученики уже уверенно владеют past tenses» без свидетельства. Если цель требует недоступного аудио, зависимые упражнения остаются незавершёнными либо получают явно авторскую, отдельно проверенную замену.

## 2. Карта курса

Назначение курса и профиль занятия — разные поля. Например, курс бытового общения может включать functional, listening, lexis и pronunciation. Назначение курса не обязует каждое занятие использовать один framework.

Обязательный минимум:

```yaml
course_id: ...
version: ...
brief_id: ...
course_intent: ...
context_overlay_ids: []
school_policy_requirements: []
entry_evidence: []
course_outcomes:
  - id: CO-01
    action: ...
    conditions: ...
    acceptable_evidence: ...
    learner_criteria: []
units:
  - id: U-01
    outcome_ids: [CO-01]
    prerequisites: []
    lessons:
      - id: L-01
        primary_profile_id: ...
        contribution_to_unit: ...
        input_evidence: ...
        target_language_or_subskills: []
        new_or_deepened: []
        retrieval_from: []
        later_return_in: []
        checkpoint: ...
    transfer_task: ...
    route_decisions: []
recycling_ledger: []
course_checkpoints: []
unresolved_dependencies: []
```

`recycling_ledger` хранит: единицу/умение, первое предъявление, последующую задачу на извлечение, применение, степень помощи, фактическое наблюдение и следующий возврат. Планируемые записи не заполняются как уже наблюдённые. Интервал выбирается под расписание и потребность; корпус не задаёт алгоритм SRS или число повторений до гарантированного освоения.

У каждого checkpoint указать решение: продолжить, дать дополнительную практику, сменить опору, вернуться к предпосылке. Например: если ученик понимает просьбу, но не может ответить без полного текста, сохранить functional-цель и добавить короткую устную репетицию со снятием текста; не объявлять освоение по matching.

## 3. Паспорт занятия

| Группа | Обязательные поля |
|---|---|
| Идентификация | `lesson_id`, `version`, `brief_id`, `course_id/unit_id` при наличии, авторская/адаптированная версия, язык инструкций. |
| Замысел | `primary_profile_id`, поддерживающие профили при необходимости, `context_overlay_ids`, `framework_id`, `framework_use_as`, `framework_rationale`, `embedded_methods`, применимые школьные требования. |
| Результат | `outcomes[]`: ID, наблюдаемое действие, ситуация, самостоятельность/допустимая помощь, продукт, критерии ученика, ограничения вывода. Для управляемого дизайна выбрать один главный результат; вспомогательные не должны вытеснять его. |
| Содержание | Целевой язык с MFP+A в нужном объёме; receptive subskills/жанр/фонологическая трудность по профилю; входные предпосылки и диагностика. |
| Маршрут | `stages[]`, диагностические развилки, время каждого маршрута, critical stages, варианты сокращения/расширения. |
| Проверка | Матрица outcome→activity→evidence→learner criteria; план task/content и language feedback, коррекция, redo. |
| Поставка | Ресурсы, роли и видимость, teacher pack, student pack, ответ/ключ/рубрика, формат платформы и ручные действия. |
| Качество | Source cards, авторские решения, `qc_results[]`, нерешённые зависимости, готовность к репетиции/пилоту, журнал версий. |

Связь основной и поддерживающей целей — проектное решение этой спецификации, а не отдельное дословное требование методистов. `framework_use_as` принимает допустимую для выбранного framework область `whole_lesson`, `activity_cycle` или `clarification_method`; у двух последних указан внешний маршрут. `embedded_methods` содержит ID метода, этап и причину включения: guided discovery не заменяет паспорт целого занятия. Полное MFP+A требуется для продуктивного целевого языка; фоновые слова рецептивного текста не превращаются автоматически в отдельный языковой урок.

### Этап и экземпляр активности

```yaml
stage_id: S-01
purpose: ...
outcome_ids: []
framework_step: ...
minutes: ...
timing_includes: [instruction, preparation, attempt, role_change, feedback]
interaction: ...
entry_condition: ...
exit_evidence: ...
if_difficulty: ...
if_already_successful: ...
activity:
  instance_id: A-L01-01
  family_id: ACT-...
  learner_operation: ...
  inputs: []
  student_instruction: ...
  teacher_actions: []
  demo_and_checks: ...
  roles: []
  information_visibility: []
  product: ...
  evidence_to_collect: ...
  support_and_fading: ...
  extensions: ...
  answer_policy: ...
  learner_criteria: []
  content_feedback: ...
  language_feedback: ...
  redo_or_next_step: ...
  platform_route: ...
  fallback_and_changed_outcome: ...
  source_cards: []
  synthesis_decisions: []
```

Семейство из библиотеки — рецепт выбора, не уже заполненное упражнение. Экземпляр должен содержать действительный текст задания, данные ролей, материалы и допустимые ответы/критерии. Поля `content_feedback`/`language_feedback` могут иметь обоснованное N/A, например в истории ради удовольствия, но не исчезают молча из запланированной практики с улучшением.

## 4. Language analysis и модель

На целевую единицу: `item`, естественный `example`, значение в этой ситуации, форма/сочетаемость, нужная произносительная особенность, register/адресат, ожидаемая трудность, способ clarification, CCQ с ответами при необходимости, практика и возврат. Продуктивная/рецептивная роль записывается явно.

Модель: ID ресурса, происхождение (`source_original`, `adapted`, `author_created`, `reported_bank`), точная версия, соответствующая задача. Таблица noticing содержит **единицу → фрагмент модели → вопрос → допустимый вывод**. У фразы вне модели статус `extension`, даже если она полезна той же теме.

Произносительная модель требует прослушанного точного фрагмента; OCR и ASR не удостоверяют IPA, ударение и интонацию. Новая запись не выдаётся за восстановленное недостающее аудио источника.

## 5. Ответ, критерии ученика и feedback

Выбрать одну политику ответа для каждой проверяемой операции:

- `closed`: ключ, допустимые варианты, основание ответа в ресурсе, правила нормализации, объяснение неоднозначностей.
- `open`: наблюдаемые критерии, приемлемые разные решения, образец с объяснением; кто и когда оценивает. Точный текст образца не является ключом.
- `intentional_error`: ошибочный стимул, задание найти/объяснить/исправить, отдельный проверенный окончательный ответ и момент раскрытия.
- `experiential_unscored`: цель участия/опыта без скрытой проверки правильности, например история ради удовольствия. При желании ученика возможен отклик, не замаскированный тест.

**Learner rubric отделена от QA.** У критерия ученика есть: конкретное действие; наблюдаемый признак; условия помощи; примеры успешного и пока недостаточного выполнения; обратная связь и следующий шаг. Рабочая шкала может быть `наблюдается самостоятельно / наблюдается с поддержкой / пока не наблюдается / нет свидетельства`. Это локальная formative-шкала, не CEFR и не IELTS.

Пример функционального результата «согласовать перенос встречи»:

| Критерий ученика | Наблюдаемое свидетельство | Обратная связь |
|---|---|---|
| Сообщает ограничение и предлагает альтернативу | Партнёр получает понятную причину и конкретный вариант | Если вариант отсутствует, запросить его и повторить реплику |
| Проверяет и подтверждает договорённость | Обе стороны называют один и тот же день/время | Сопоставить записанные итоги; исправить расхождение |
| Выбирает уместный способ просьбы | Реплика подходит отношениям и ситуации; целевые средства помогают смыслу | Разобрать реальную реплику и повторить с подходящим выражением |

Требование употребить ровно шесть фраз не добавляется ради подсчёта. Один такой эпизод свидетельствует о конкретной задаче в этих условиях, не об общем владении языком.

## 6. Ресурсы и три слоя пакета

`assets[]`: ID, путь/проверенный URL, происхождение, автор/право использования или известная зависимость, версия/хеш при наличии, страницы/таймкоды, длительность, transcript/alt при необходимости, связанные задания, ключ и статус фактической проверки. Для собственного текста тоже указывается авторский статус. Наличие URL не означает доступность содержимого.

**Ученический пакет:** понятная задача, нужные входные данные, разрешённые опоры, способ ответа и критерии в уместном объёме. **Пакет преподавателя:** цель, timing, инструкция/demo, мониторинг, решения при затруднении, ключи, feedback и технические действия. **Запись проверки:** версия, применимые QC/PLAT, фактические результаты и зависимости. Видимость этих слоёв проверяется по возможностям формата; разделение заголовками внутри общего HTML не делает ключ секретным.

## 7. Минимальная запись QA и готовности

```yaml
qc_id: QC-...
applies: true
status: unknown
evidence: ...
reviewed_version: ...
review_method: ...
finding: ...
repair_or_next_check: ...
readiness: authoring_draft
```

- `authoring_draft`: материал проектируется или имеет незакрытые authoring-проверки.
- `ready_for_rehearsal`: все применимые authoring critical/major проходят; runtime ещё проверяется. Для N/A есть основание.
- `ready_for_pilot`: дополнительно пройдены применимые runtime-проверки конкретной версии. Это не `pilot_passed`.
- `pilot_reviewed`: занятие действительно проведено; есть фактический отчёт, ограничения и решение о доработке. Не означает автоматического разрешения на публикацию или доказанного общего эффекта.

Это рабочие статусы методического процесса, не существующие API-статусы RiseAcademy. Требования — в [рубрике качества](quality-rubric.ru.md); основания архитектуры курса/занятия и точные source cards — в [общих правилах](core-rules.ru.md).
